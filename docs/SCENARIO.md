# 시나리오 — 기업 지급의 통제와 정보 보호

대상은 기존 기업 지급 시스템을 온체인으로 확장하려는 은행·핀테크 엔지니어입니다. 기존 시스템 내부의 통제만 필요하다면 Maroo가 반드시 필요한 것은 아닙니다. 이번 실습은 온체인 실행까지 승인 상태를 전달하고 강제할 수 있는지를 검증합니다.

## 프로그램 1 / 지급할 자격이 있는가?

은행의 기업 심사 → 승인 증명 발급·인덱싱 → 기업의 지급 요청 → PCL 프록시 정책 검사 → OKRW 지급 또는 차단 → 기존 요청과 결과 대조.

심사·원장·대사는 업무 맥락이며 구현하지 않았습니다. 실제 구현은 프록시, 정책, 데모 EAS, OKRW 지급과 결과 검증입니다. 수취인 KYB나 실제 법규 준수를 검증하지 않았습니다.

| 역할 | 책임 |
|---|---|
| 은행 심사 담당 | 승인 여부 결정. 실습에서는 설명만 |
| 증명 발급자 | 데모 증명 발급·폐기. 운영용 발급자 제한 미검증 |
| 정책 관리자 | 자신이 배포한 프록시 정책 설정 |
| 기업 지급 계정 | 지급 요청 서명 |
| 공급업체 계정 | tOKRW 수취 |

## 프로그램 2 / 수취인이 비공개 지급을 확인할 수 있는가?

로컬 Clairveil에서 Alice가 10 uclair 예치 → Bob에게 7 지급 → Alice 3 / Bob 7 scan 확인. uclair는 로컬 단위이며 OKRW와 연결하거나 교환하지 않습니다. PCL과 Privacy는 이번 제출에서 별도 실행 경로입니다.

## 실제로 배운 점

- Denylist 및 EAS 유효성은 앱 사전검사를 넘어 실제 포함 거래에서 지급을 차단했습니다.
- false 증명도 통과했습니다. 유효한 증명 보유와 데이터 값 검사는 별개입니다.
- 프록시를 호출한 실행과 구현체 직접 호출을 구분해야 합니다. 실습 계약은 직접 호출을 proxy-only로 거절합니다.
- 로컬 proof 성공은 Maroo verifier 호환성의 증거가 아닙니다.
