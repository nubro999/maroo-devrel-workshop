# 변경 가능한 시나리오

상태: 설계 가정. 제목: **Compliant Confidential Vendor Payment**.

기업 지급 담당자 Alice가 KYB된 공급업체 Bob에게 테스트 OKRW를 지급합니다. 목표는 PCL 정책 판단과 Privacy 데이터 가시성을 설명하는 것입니다. 법적 적합성 인증이나 완성된 기업 지급 시스템을 주장하지 않습니다.

## 이야기의 우선순위 — 사용자 결정

핵심은 **잘못된 지급 방지**다. 조직이 규제·내부 기준을 검토해 실행 가능한 지급 정책을 정하고, 그 정책을 충족하는 지급만 실행하는 여정을 보여준다. Privacy도 필요하지만, 이야기에서는 적격 지급의 정보 공개 범위를 다루는 다음 질문으로 배치한다.

정책을 정하는 책임과 시스템이 정해진 정책을 집행하는 역할을 구분한다. PCL 사용 자체를 법적 규제 준수 인증으로 표현하지 않는다.

제안 여정: 지급 요청 → 수취인 자격·금액 등 조건 확인 → 정책에 따른 허용/거부 → 허용된 지급 실행 → 수취 및 감사 증거 확인. 이는 목표 설계이며 현재 구현 상태를 뜻하지 않는다.

첫 PoC의 비교 실험 후보:
- 자격과 한도 조건에 맞는 지급은 실행된다.
- 금액만 한도를 넘기면 지급이 거부된다.
- 수취인 자격만 달라지면 지급이 거부된다.

조건·한도·자격 표현은 아직 미확정이다. 공개 PCL/EAS 인터페이스, 테스트넷 정책 설정과 호출 권한을 확인한 뒤 실제 재현 가능한 비교 실험부터 선정한다. 클라이언트 사전 확인과 실제 실행 경로에서의 정책 강제를 구분한다. 거부 시 지급액 이동 여부와 가스 비용 발생 여부도 별도로 기록한다.

현재 native 송금 스크립트는 기본 연결·가치 이동 확인용이며 위 업무 정책을 구현하지 않았다. Privacy는 유효한 Maroo 실행 선행 조건과 Clairveil 로컬 재현 범위를 분리해 검증한다.

| 항목 | 현재 가정 |
|---|---|
| 대상 조직 | 한국 핀테크의 기업 자금관리팀 |
| 가치 흐름 | 지급자 → 공급업체 |
| 학습자 | EVM/TypeScript에 익숙한 시니어 엔지니어 |
| OKRW | native 투명 송금으로 첫 상태 변경 확인 |
| PCL | 정책이 실행/거부에 미치는 효과 검증 예정 |
| Privacy | deposit → transfer → recipient scan 검증 예정 |
| EAS | KYB 자격을 연결하는 확장 설계, 미구현 |
| 감사자 | disclosure 권한과 키 관리 논의, 미구현 |

주제를 바꾸면 이 문서, workshop 예시만 함께 수정합니다. 주소·RPC·전송 로직에는 업종별 규칙을 넣지 않습니다.

공개 체인의 투명 송금은 송신자·수신자·금액이 드러납니다. 별도의 Clairveil 로컬 실행과 하나의 비공개 live 거래인 것처럼 연결하지 않습니다. note plaintext와 spending/viewing/audit key의 보관 주체, remote prover의 입력 가시성, disclosure 수신 권한은 별도로 검토해야 합니다.
