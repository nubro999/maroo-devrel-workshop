# 시나리오: 승인된 기업의 지급을 실행하기

은행은 이미 기업을 심사하고 지급을 통제합니다. 이번 시나리오는 지급을 온체인으로 확장할 때, 그 승인 조건을 체인에서도 지킬 수 있는지 확인하는 데 초점을 둡니다.

## 지급 통제: Maroo

1. 은행이 기업을 심사하고 지급 서비스 이용을 승인합니다.
2. 발급자가 승인된 기업의 계정에 EAS 증명을 발급합니다.
3. 기업이 PCL에 등록된 프록시로 지급을 요청합니다.
4. PCL이 설정된 조건을 검사합니다.
5. 조건을 통과하면 지급하고, 위반하면 거절합니다.

은행 심사와 원장 연동은 이 시나리오의 배경입니다. 구현한 것은 실습용 프록시, 정책 설정, 자체 발급 EAS 증명, tOKRW 지급과 결과 확인입니다. 실제 KYB나 법규 준수 전체를 검증한 것은 아닙니다.

| 역할 | 하는 일 |
|---|---|
| 은행 심사 담당 | 승인 여부 결정. 이번에는 설명만 제공 |
| 증명 발급자 | 증명 발급·폐기 |
| 정책 관리자 | 자신이 관리하는 프록시의 지급 조건 설정 |
| 지급 계정 | 지급 요청에 서명 |
| 수취 계정 | tOKRW 수령 |

실습에서는 한 계정이 여러 역할을 겸합니다. 운영 환경의 역할 분리와 발급자 제한은 별도로 설계해야 합니다.

## 비공개 지급: 로컬 Clairveil

Alice가 10 uclair를 예치하고 Bob에게 7을 보냅니다. 이후 각 지갑에서 Alice 3, Bob 7을 확인합니다. 이 실습은 Maroo 테스트넷과 별개인 로컬 체인에서 실행합니다. uclair와 tOKRW는 서로 다른 자산입니다.

## 결과를 어떻게 해석하나요?

- Denylist에 송신자를 넣으면 같은 지급이 차단됩니다. 지급액은 전달되지 않지만 실패 거래의 수수료는 발생합니다.
- 기본 시나리오에서 승인 여부는 증명 발급·폐기로 표현합니다. 데이터 조건에 관한 추가 발견은 [정책 해석 주의사항](POLICY_CAVEATS.md)에 정리했습니다.
- 구현체 직접 호출을 막는 proxy-only 검사는 실습 계약의 별도 보호장치입니다.
- 로컬 Privacy 성공만으로 Maroo의 verifier와 호환된다고 판단할 수 없습니다.
