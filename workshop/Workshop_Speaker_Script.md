# Workshop Package — 진행 대본

**70분 · 사전 준비 제외 · 한국어 엔지니어 대상**

면접 제출용 5–8분 영상과 별개인 워크숍 자료입니다. 슬라이드의 실행 수치는 기존 검증 기록이며, 참가자의 당일 실행 결과와 구분합니다. 전체 참가자 리허설은 아직 수행하지 않았습니다.

자료: https://github.com/nubro999/maroo-devrel-workshop

## 01. 승인된 기업만 지급할 수 있는가?
**00–02분 · 2분 · WORKSHOP**

오늘은 승인 상태가 실제 지급 실행에도 적용되는지 확인합니다. 앞에서는 테스트넷 지급 통제, 뒤에서는 독립된 로컬 Privacy 흐름을 실행합니다. 기관의 심사와 원장 통합을 완성했다고 주장하지 않습니다. 실습 준비는 수업 전에 끝났다는 가정입니다.

## 02. 은행의 승인 상태를 체인 실행까지 전달합니다
**02–05분 · 3분 · BUSINESS**

은행 내부 지급 통제만 필요하다면 Maroo가 반드시 필요한 것은 아닙니다. 대상은 온체인으로 지급을 확장하는 엔지니어입니다. 앱이 잘못된 요청을 보내더라도 체인 실행에서 조건이 유지되는지 묻습니다. BIS의 토큰화 논의는 배경이며 우리 실험이 은행 간 대사 비용을 검증한 것은 아닙니다.

## 03. 익숙한 EVM 호출에서 체인 기능까지
**05–07분 · 2분 · ARCHITECTURE**

구조 소개는 역할 수준으로 제한합니다. 프리컴파일 자체와 관리자가 변경하는 정책 설정을 구분합니다. EVM 도구를 유지하면서 체인 기능을 호출할 수 있다는 점이 참가자에게 중요합니다. 출처: docs.maroo.io/concepts/compliance 및 저장소 공식 ABI.

## 04. EAS는 자격 기록, PCL은 실행 조건 검사
**07–10분 · 3분 · CONCEPT**

EAS attestation과 ZK proof는 다릅니다. EAS가 기업 심사를 수행하지 않습니다. 실습에서는 본인 계정이 데모 자격을 발급합니다. 실제 은행에서는 누가 발급할 수 있는지 별도 통제가 필요합니다. 유효한 증명이 존재한다는 것과 그 안의 bool이 true라는 것은 다른 조건입니다.

## 05. 지급 요청은 PCL에 등록된 프록시로 보냅니다
**10–13분 · 3분 · LIVE**

사용자는 preCall/postCall을 각각 호출하지 않습니다. 프록시 주소와 지급 ABI를 사용합니다. 구현체를 직접 호출하면 프록시 정책 경로와 달라지므로 실제 자산·권한을 보호해야 합니다. 실습 구현은 proxy-only와 owner 검사를 포함합니다. 이는 PCL과 별개인 계약 보호입니다.

## 06. 70분 동안 두 환경의 증거를 모읍니다
**13–15분 · 2분 · AGENDA**

설치·빌드·회로 생성은 사전 준비입니다. 전체 참가자 시간 리허설은 아직 하지 않았습니다. 독립 PoC 다음 단계 강의는 없고 결과 해석으로 마칩니다. 조직 적용 후속 항목은 참가자 문서에 남겼습니다.

## 07. 실습 준비 / 네트워크와 지급 계정을 확인합니다
**15–17분 · 2분 · LIVE**

자신의 지급 계정과 수신자를 확인합니다. 참가자가 이전 제출자의 주소를 무조건 사용하지 않도록 합니다. 기본 lab 명령은 안내만 출력합니다. 이번 실습은 실제 테스트넷 수수료가 들며 실패 거래도 예외가 아닙니다.

## 08. 실습 1 / 프록시에서 지급과 차단을 비교합니다
**17–22분 · 5분 · LIVE**

5분 동안 wrapper가 배포와 두 거래를 수행합니다. 스크립트에 전역 정책 변경이 없고 자신의 프록시만 변경하는 것을 보여줍니다. 결과의 hash와 포함 영수증을 대조합니다. 지연 시 최대 3분 진단 후 저장 증거 분석으로 전환하고 실제 실행 여부를 표시합니다.

## 09. EAS는 발급 이후 인덱서 등록도 확인합니다
**22–24분 · 2분 · LIVE**

실제 실험에서는 attest 성공 직후 indexed=false와 count0이었습니다. 인덱서 등록을 추가한 뒤 EAS 지급이 통과했습니다. 카운트는 폐기된 증명도 포함하므로 개수만으로 유효성을 판단하지 않습니다. 출처: EAS_LIFECYCLE_EAS_RESULT.json.

## 10. 실습 2 / 자격이 없으면 지급되지 않습니다
**24–27분 · 3분 · LIVE**

lab:eas가 일련의 실험을 수행하는 동안 단계별 출력을 관찰합니다. 정책의 오류를 RPC 장애나 잔액 부족과 혼동하지 않습니다. 기존 기록 블록19181675를 열어 실패 영수증과 과거 블록 오류 재확인을 보여줄 수 있습니다.

## 11. 실습 2 / 자격 발급 후 지급이 완료됩니다
**27–30분 · 3분 · LIVE**

성공 기준은 해시가 아니라 포함 영수증, 이벤트, 상태 변화입니다. 이미 실행한 성공 거래 f7062181…를 보여줄 때 과거 실행 기록이라고 명시합니다. 이 자격은 실제 은행 심사가 아니라 데모입니다.

## 12. 실습 2 / 자격을 폐기하면 다시 차단됩니다
**30–34분 · 4분 · LIVE**

폐기 후 동일한 지급 요청을 직접 전송해 실패를 확인했습니다. 정책은 실험 후 원래 상태로 복원합니다. 참가자에게 누가 폐기 권한을 갖는지 묻습니다. 실제 발급자 통제와 은행의 승인 취소 절차는 다음 설계 경계이며 이 데모로 완료하지 않았습니다.

## 13. false인 증명도 지급이 통과했습니다
**34–37분 · 3분 · LIVE**

추가 명령은 npm run lab:boolean -- --broadcast입니다. 기본 수업에서는 저장된 실제 기록을 분석하고 빠른 참가자는 직접 실행합니다. 새 스키마·동일 만료·부가 데이터로 비교했고 false 증명을 폐기한 다음 true를 발급했습니다. 증명 데이터를 다시 읽었습니다. 두 건 모두 PolicyCheckPassed가 나왔습니다.

## 14. 유효한 자격과 데이터 값의 참·거짓은 다릅니다
**37–40분 · 3분 · DISCUSS**

false 동작을 버그라고 단정하지 않습니다. 이번 정책 설정의 실행 의미입니다. 다른 정책이나 resolver까지 일반화하지 않습니다. 은행은 유효한 증명 보유를 승인으로 쓰는지, 페이로드 조건을 검사해야 하는지 결정해야 합니다. 승인하지 않은 대상에게 false 증명을 발급하면 이 설정에서는 지급을 막지 못합니다.

## 15. 프로그램 2 / 지급 정보의 공개 범위를 다룹니다
**40–43분 · 3분 · LOCAL**

기업은 지급 조건을 지키면서 지급 관계와 금액의 공개 범위를 통제하려 할 수 있습니다. 모든 단계의 모든 정보가 숨겨진다고 설명하지 않습니다. 공개 예치와 shielded note를 구분합니다. PCL 실험 결과와 로컬 Privacy를 하나의 Maroo confidential payment로 합치지 않습니다.

## 16. Maroo와 Clairveil 결과를 분리합니다
**43–45분 · 2분 · BOUNDARY**

Maroo Privacy용 유효 payload를 만들 선행 연결을 확보하지 못했습니다. proof 거절을 관찰한 것이 아니라 생성 준비 단계에서 막혔습니다. 체험 사이트의 simulation은 실제 EAS 자격 발급 증거로 사용하지 않습니다. 로컬 proof를 호환한다고 추정해 전송하지 않았습니다.

## 17. 키와 공개 데이터의 경계를 먼저 확인합니다
**45–47분 · 2분 · LOCAL**

노트 소유자·수신 지갑·prover·감사 주체를 구분합니다. 이번에는 로컬 prover와 개발용 아티팩트를 사용했습니다. 공개용 JSON만 보여주고 지갑 키·raw notes는 열지 않습니다. 감사 config가 있다는 이유로 실제 복호화 성공을 주장하지 않습니다.

## 18. 실습 3 / 예치하고, 보내고, 수신 결과를 찾습니다
**47–57분 · 10분 · LOCAL**

10분 실행 구간입니다. 사전에 준비한 고정 소스와 아티팩트를 사용합니다. run-local.py --source PATH --run-dir NEW --artifacts PATH --go GO를 LOCAL_RUN 안내에 따라 실행합니다. 빌드 캐시가 없다면 시간 초과가 가능하므로 사전 리허설이 필요합니다. 자동 dummy 준비가 현재 버전에서는 self batch라는 점을 설명합니다.

## 19. 실습 3 / 성공은 받는 사람의 상태로 판단합니다
**57–62분 · 5분 · LOCAL**

5분 동안 PUBLIC_RESULT를 분석합니다. 노드 종료까지 wrapper가 처리합니다. 기존 증거를 보면 직접 실행 성공과 구분합니다. 독립 재현은 계정과 genesis가 새로웠지만 build/artifact cache는 재사용했음을 명시합니다. uclair는 로컬 자산이며 OKRW와 전환하지 않았습니다.

## 20. 실패 결과도 개발자가 읽을 수 있어야 합니다
**62–65분 · 3분 · DX**

Explorer의 Raw를 IPcl ABI로 parseError하면 정확한 주소를 얻습니다. 내부 문자열 변환 구현은 확인하지 않았으므로 확정 원인으로 단정하지 않습니다. UI 보고와 실행 증거의 강도 차이를 구분합니다. 3분 이상 환경 장애가 계속되면 실제 기록 분석으로 전환합니다.

## 21. 지금 우리가 증명한 범위는 어디까지인가?
**65–68분 · 3분 · DISCUSS**

참가자에게 각 환경에서 한 문장으로 검증한 것을 말하게 합니다. 기존 시스템의 심사와 PCL의 실행 검사를 구분할 수 있어야 합니다. 자체 데모 자격이 은행 승인으로 성립하려면 어떤 통제가 필요한지 묻습니다. 이 질문은 로드맵 강의가 아니라 결과의 한계를 해석하는 질문입니다.

## 22. 내 실행 증거를 남깁니다
**68–70분 · 2분 · CHECKOUT**

실행하지 않은 항목을 성공으로 세지 않습니다. 참가자별 결과를 기록하고 마칩니다. 정책 복원·데모 증명 폐기·로컬 노드 종료 상태를 확인합니다. 조직별 추가 확인 항목은 문서에 있고 별도 PoC 마무리 강의는 하지 않습니다.
